# Brief lock

Failure this prevents: research and option menus drifted away from the agreed core ("a fast light show of one organic mass"); the user picked from options that no longer contained the core, and the build was rejected.

## Steps
1. **Write the core in one line** in the user's words, plus 3–5 hard constraints and known rejections (e.g. *no lines, no literal motifs, not slow*). Show it and get a yes.
2. **Separate scope words.** "Ignore my taste" during research ≠ drop the core. When an instruction could loosen the core, ask which part it applies to.
3. **Every option must contain the core.** When offering choices, each option varies only *how*, never *whether* the core is kept. Write the core at the top of the question.
4. **Pre-mortem before building:** "Which agreed constraint could this break?" — check rejections list.
5. **First deliverable = smallest thing that proves the core** (10–30 s preview), then grow.
6. **After a rejection:** quote the core, name exactly which part was broken, fix that first; don't add new ideas in the same round.
7. Keep `BRIEF.md` in the project; update it only with the user's explicit approval.
